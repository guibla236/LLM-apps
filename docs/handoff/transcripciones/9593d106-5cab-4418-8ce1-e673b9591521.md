## ✅ Review of changes (branch `feat/model-evaluator-for-rag-and-ft` vs `main`)

### 🔍 High-level scope
This branch adds a full “async evaluation” workflow for admin users:

- **Backend**: New evaluation module (`async_rag_evaluator.py`) that runs DeepEval metrics over uploaded JSON results + gold data, stores task progress in memory, and writes per-question CSV output.
- **API**: New admin endpoints to start evaluation, poll status, and download CSV.
- **UI**: Dashboard section + JS to drive the workflow (upload, poll + download).

---

## ✅ What’s good / strengths
- **Separation of concerns**: evaluation logic is isolated in its own module.
- **Configurable metrics** (via  list) and extensible metric instantiation.
- **Async background task** (FastAPI ) prevents blocking the request.
- **Clear UI flow**: start → poll → download → feedback/status colors.
- **Good validation path**:  checks the presence of required fields before starting.

---

## 🛠️ Key issues & improvement opportunities

### 1) **In-memory task tracking is volatile**
 lives only in process memory:
- Restarting the server loses all tasks & CSV paths.
- Multiple workers (Gunicorn/Uvicorn with workers) won’t share state.

**Recommendation:** persist status/paths in MongoDB (existing DB dependency exists) or use a shared cache (Redis).

---

### 2) **CSV cleanup / disk management**
Generated CSVs are named like `eval_{system_type}_{task_id[:8]}.csv` and stored in the working directory indefinitely.

**Risks:**
- Disk growth over time.
- Name collisions if multiple tasks start rapidly (though unlikely).

**Suggestion:** write to a dedicated folder (`/tmp/evals/`), include timestamp, and add a cleanup job or TTL policy.

---

### 3) **Fixed 30s sleep between examples may be excessive**
`await asyncio.sleep(30)` is hardcoded per item; for large data this becomes very slow.

**Suggestion:** make rate limit configurable (env var), or implement batch scoring + backoff, or move to a rate-limited queue instead of fixed sleep.

---

### 4) **Potential performance / blocking in DeepEval usage**
 is called synchronously via  (probably fine), but:

- If  is blocking, evaluation blocks the background task thread.
- It might be better to use an async model interface if available (or offload to an executor).

---

### 5) **Golden-matching logic could be more robust**
Matching gold record via:

```py
gt = next(
    (g["expected_output"] if "expected_output" in g else g["answer"] for g in golden_data if g.get("question") == q),
    "No GT found"
)
```

If  is empty or duplicates exist, it may match incorrectly. Also, `question` vs  mismatch could still happen.

**Suggestion:** require an explicit `id` field in both files (or enforce exact schema), or fallback to using list index alignment only if there is no match.

---

### 6) **Missing server-side validation for upload size / JSON shape**
The endpoints accept uploaded JSON without:
- size limits
- schema checks beyond a few fields

This can be exploited to upload huge JSON and OOM the server.

**Suggestion:** add request size limits (FastAPI/Form limits or reverse proxy) and validate schema with Pydantic models that enforce max lengths.

---

### 7) **UI/JS: minor UX improvements**
- The download button is hidden until completion; good. But if status goes to “failed”, the user never gets a retry or error detail (beyond being shown  in status). Perhaps show a clearer error panel.
- The polling interval is hardcoded to 5s; could be a bit lower/higher depending on expected latency.

---
