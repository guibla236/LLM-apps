# Migrate ingestion pipeline from Pinecone to MongoDB

## Meta

- **Milestone**: M8 — Vector Backend Migration (Pinecone → MongoDB + Voyage AI)
- **Labels**: `initiative:vector-backend-migration`, `phase:ingestion`, `type:refactor`, `priority:high`, `area:backend`, `area:mongodb`
- **Estimate**: 1 day
- **Depends on**: Issue #15 (new vector store available)

## Description

As an AI Engineer, I want to migrate the ingestion pipeline from Pinecone upserts to MongoDB document inserts, so that ingested QA pairs are stored as MongoDB documents with Vector Search auto-embedding handled server-side by Voyage AI.
**Important**: This migration only covers the QA corpus (Stack Exchange pairs). The synthetic Knowledge Bases (KB1001, KB1004, etc.) are **not migrated** — they were generated by LLMs, never reviewed, and the real QA corpus makes them redundant. The `kb_docs` collection and the old `PINECONE_KB_INDEX_NAME` are deprecated.
### Changes needed

#### `api/modules/rag_tickets_ingestor.py`

- Replace `vector_store.add_texts(texts=splits, metadatas=[...], ids=ids)` with `collection.insert_many(documents)`.
- Each document is now a full MongoDB document: `{ticketId, title_body, upvoted_answer, community, priority, expected_output}`.
- No need to chunk `title_body` — MongoDB's `autoEmbed` handles the text as-is.
- No need to truncate `expected_output` to 500 chars for metadata — it's a regular field in the document.

#### `api/modules/rag_kb_ingestor.py` (not migrated — deprecated)

- This module handled synthetic KB ingestion. With the migration, it is **deprecated** and should not be called during startup or deployment. The synthetic KBs are not migrated.
- The file can remain in the codebase for reference.
- In a future initiative (`initiative:real-ms-docs-ingestion`), a new KB ingestor can be written for real documentation.

#### `api/scripts/ingest_stackexchange_dataset.py` (from Issue #4)

- Replace Pinecone `upsert` with MongoDB `insert_many`.
- Replace Pinecone `list` (for `--resume`) with MongoDB `find({}, {ticketId: 1})` to get existing IDs.
- The `qa_pairs` collection (from Issue #8) becomes the primary data store — no separate Pinecone write.
- This simplifies the script significantly: one write (Mongo) instead of two (Pinecone + Mongo).

#### `api/scripts/build_bm25_index.py` (from Issue #5)

- Read from MongoDB `qa_pairs` collection instead of separately.
- The JSON structure of `bm25_index.json` stays the same.
- **OR**: if M4's hybrid ranking native option is implemented (see Issue #17), this script may be replaced entirely by Atlas Search full-text + `$rankFusion`.

### Notes

- With auto-embedding, MongoDB starts building the Vector Search index as soon as documents are inserted. You can monitor progress in the Atlas UI.
- The first ingestion will trigger index building, which may take minutes for 60K documents.
- Chunking is now optional — MongoDB can handle long text fields. But if `title_body` exceeds the model's context window (32K tokens for `voyage-4-lite`), it will be truncated automatically by Voyage.
- The `bm25_index.json` local file may become obsolete if we implement native hybrid ranking (Issue #24). Keep it as fallback during the transition.
