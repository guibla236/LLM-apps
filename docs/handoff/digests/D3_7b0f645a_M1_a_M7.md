## M1 — Ingesta y realineación de paradigma (turnos 1–~62)

**Qué se hizo**
- Plan de ingesta por comunidad con `--communities`, `--resume`, verificación por lote y barra de
  progreso (el usuario exigió ver progreso: “¿cómo que silencioso?”).
- Descubrimiento de que había que **rehacer la ingesta** excluyendo IDs del Golden (`--exclude-golden-ids`),
  porque el golden se había construido sobre el mismo corpus.
- Chunking aplicado de verdad (el usuario detecta que el primer intento **no** chunkéo).
- `payload too large` de Pinecone en la primera comunidad → batches adaptativos.
- IDs determinísticos `md5(title_body)[:12]` (evita la aleatorización de `hash()` entre procesos).
- Prompts reescritos de “ticket” a “Q&A directo”; se elimina la respuesta en formato ticket.

**Resultado**: 60.161 docs en Mongo, 81.599 vectores en `kb-se-all`, 12/12 comunidades, 0 duplicados.

**Lección operativa**: se perdió trabajo por una ingesta lanzada en terminales que después se
cerraron; quedó como regla “los procesos largos van con log en vivo y script reanudable”.

## M2 — Golden QA y evaluación limpia (turnos ~63–120)

**Qué se hizo**
- Golden de 200 pares estratificados; submuestra de 50 (seed 42) para las corridas.
- Pipeline `run_eval.py` con DeepEval: reintentos ante 429, reanudación con `--append-to`, CSV+JSON.
- Cambio de proveedor **Groq → OpenRouter** (Groq quedó chico para el volumen de evaluación).
- Se arreglan tres bugs que arruinaban las métricas: namespace, metadata `ticketId`/`text`, y
  re-sort del híbrido que hoisteaba BM25.
- El usuario detecta que el evaluador estaba evaluando **tickets en español y KBs** (legacy) en vez
  del corpus nuevo → se corrige el `search_type` a `tickets_only`.

**Resultado**: tabla de M2 (vector_only 24% vs hybrid 36% de Correctness). La caída de Correctness
frente al sintético se interpreta como desaparición del sesgo, no como regresión.

**Discusión metodológica importante**
- El usuario cuestiona usar el **mismo modelo como generador y juez**; se acepta el sesgo y se
  documenta, y en M4 se cambia a juez independiente (`gpt-5.6-luna`).
- “¿Cómo justificamos la necesidad de un RAG si la búsqueda semántica devuelve basura y solo BM25
  levanta las métricas?” → pregunta que origina M4.

## M4 — Optimización de retrieval (turnos ~170–350) — la etapa más densa

**Qué se hizo**
- Benchmark de embeddings (Voyage tiers, qwen3, all-minilm) y chunking; corridas P0/P1.
- Migración de BM25 local → **MongoDB Atlas Search** (se elimina `rank-bm25` y el JSON del repo).
- Experimento de expansión de contexto (P1 expanded) controlado por flag.
- Cambio a juez independiente `gpt-5.6-luna`; análisis de “DeepSeek subestima” y re-escritura de
  tablas del blog para no mezclar jueces.
- Batches adaptativos de Pinecone para el reindexado con `voyage-4-lite`.

**Resultado**: gana P1 (`voyage-4-lite`, 1000/100). CP 60,33% → 69,40%. El híbrido **empeora** CR
(−2,72) → `vector_only` como default de producción.

**Conflictos que hay que recordar**
- El usuario exige que cada tabla del blog se verifique empíricamente (“evitando alucinaciones”) y
  que los logs estén en la carpeta de la entrada que los cita (hubo logs `m2_*` mal ubicados).
- Discusión recurrente sobre **no cambiar dos variables a la vez** (expansión de contexto vs k).
- Decisión de no usar worktrees todavía (trabajo secuencial).
- Rebase/merge de M4 sobre la branch de M2/M3 → origen de la divergencia actual entre
  `feat/search-optimization` y `feat/cost-optimization-benchmark` (ver [H-11](../03_HILOS_ABIERTOS.md)).

## M6 — Benchmark de costo/latencia (turnos ~350–470)

**Qué se hizo**
- Se replantea M6: **benchmark, no router**. Golden de 75 estratificado en 3 buckets de complejidad
  (25/25/25), k=10 para comparabilidad con M4, juez `gpt-5.6-luna`.
- Se agrega `--generator-model` al evaluador y se registran modelos nuevos (`ling-2.6-flash`,
  `gemini-3.5-flash-lite`).

**Resultado**: tabla de M6 (DeepSeek 0.465 correctness; Ling frontera de Pareto; Gemini latencia
pero calidad 0.161). Decisión: DeepSeek generador único.
